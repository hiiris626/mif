# 验证超时排查与修复（2026-09-28）

## 已确认的故障位置

旧任务于2026-09-28 01:08:46触发NCCL watchdog，随后退出。错误为rank 0的ALLREDUCE，NumelIn/Out=64，等待2700000毫秒。日志先记录了第7轮训练结束、开始56832个patch的验证。

64个元素对应EvaluationLossAccumulator的4×16充分统计量（逐通道MSE分子、有效像素数、重叠损失和、有效图数）。因此故障定位于验证末尾loss全局汇总，而不是训练反向传播。第6轮last.pt已完整保存，第7轮没有checkpoint。

旧实现各卡独立遍历验证集，并将每个batch的完整概率搬回CPU做NumPy统计；快卡完成后直接发起NCCL汇总，没有中途同步、进度诊断或加载超时。旧6轮验证耗时分别为914、1324、1368、1725、846、2034秒，波动很大。这种路径存在长时间跨卡等待的风险。

日志没有记录其他rank当时停在哪个batch或调用栈，因此不能断言具体哪个worker、GPU或外部任务是最初触发因素，也不能把观察到的超时归因成已证实的硬件故障。

## 实施的修复

1. 逐像素分类统计在设备上累计，只在结束时导出小型混淆矩阵、直方图和标量。统计定义保持一致，float64用于加权累计，计数为int64。
2. 验证损失、分类指标及患者支持数的跨卡归并改用独立Gloo/CPU通信组，不再提前在GPU上启动验证统计的NCCL等待。
3. 每8批通过CPU monitored_barrier检查各rank到达情况，等待上限5分钟，能报告未到达rank。循环长度取各rank最大批数，无样本rank也走相同心跳路径，不填充/重复/丢弃验证样本。
4. 每个rank持续更新validation_progress/validation_rank_N.json，记录取数、前向、指标计算、等待其他rank、统计归并和完成阶段。控制台每20批打印每卡进度。
5. 数据加载器增加180秒取数超时，避免worker无限阻塞。

未通过加长45分钟NCCL超时来掩盖问题。模型结构、训练loss、优化器、学习率调度、患者划分、通道阈值和缓存标签均保持原定义。
