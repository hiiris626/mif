# 训练速度分析（2026-09-27）

结论：当前数据供给受机械盘随机读限制；平衡清单全量合并和更多 epoch 增加总工作量。首次按 50 步推算 9–10 天只适用于后续速度不改善的情形，不应视为确定完成时间。此次仅诊断，未更改或停止正式训练。

## 已核对的工作量

可直接比较的历史记录为 `/data/weiyh/logs/vitmatte_v3_256.log`，15 轮运行约 8.5 小时。用户提到的 2–3 天尚不能确认对应哪一轮；旧报告中还记录了 v2 独占资源约 2.5 天的预估。

| 项目 | 历史 v3 | 当前 |
|---|---:|---:|
| 四卡全局 batch | 256 | 256 |
| 输入 / ViT 尺寸 | 256 / 224 | 256 / 224 |
| 每轮训练条目 | 295096 | 738752（含跨通道重复抽样） |
| 训练轮数上限 | 15 | 40 |
| 每轮更新数 | 1152 | 2885 |
| 最大更新数 | 17280 | 115400 |
| 训练中每次验证样本 | 约400 | 56832，全量分布式 |

当前自然训练集226465个patch，平衡清单738752条，对应218672个不同patch。同一个patch出现在多个通道平衡清单中，会多次训练。这使每轮条目是自然训练集的3.26倍、旧v3每轮的2.50倍。结合40/15轮，总更新量是旧v3的6.68倍。各通道清单内的2:1:1比例并不要求每个epoch把所有清单完整遍历；若改成固定抽样预算，可缩短每轮，但也改变总训练暴露量，不能把它称作同等工作量的性能加速。

## 当前瓶颈证据

`/data`挂载在旋转机械盘sdb（ROTA=1）。第一轮短时采样中，盘忙碌度92–96%，读取8–13 MB/s，读请求平均等待74–84毫秒，队列约15–21；后续采样有波动，详见review/performance_20260927/disk.txt。

当前PixelDataset每次取样均打开JPEG和16/17通道TIFF，重新解码、生成组织掩膜和标签，再执行增强及缩放，没有使用预处理张量缓存。四卡16个worker并发随机读同一机械盘，DDP又需等待最慢rank，数据供给成为明显瓶颈。已有统计预处理完成不等于训练输入已缓存。

GPU短时观察出现一张卡0%、其他卡100%但显存控制器利用率0%、功耗约86–112W的组合。这与同步等待相符；仅凭nvidia-smi的GPU百分比不能断言计算单元已有效满载。尚未用逐算子profiler测得精确等待时间比例。

旧加载器支持memmap缓存，磁盘上也存在缓存文件；旧日志没有明确的缓存命中记录，因此不能断言该历史运行必然使用了这些缓存。旧缓存的划分、插值及回归目标处理也不能直接代替当前多标签原生掩膜语义。

## 时间估计为何需要修正

当前第100步累计638.98秒；第50–100步用299.06秒，约5.98秒/步。历史v3第1轮日志区间约6.90秒/步，第8–15轮约1.02–1.23秒/步，说明历史运行后期明显加速。文件页缓存变热可能是原因之一，但未通过当时的性能记录证实。

按当前5.98秒/步不变，115400步训练约191.7小时（约8天），还需另计完整验证及最终评估。若能达到旧运行平均1.776秒/步，同样115400步约56.9小时（约2.4天）；这是条件推算，旧均速还包含旧验证/保存开销，且当前有SyncBN、分布式MSE+Dice和更完整验证，不能承诺一定达到。

## 优先优化方向

1. 按当前原生分辨率标签定义建立缓存，保存H&E、组织掩膜、多标签与忽略掩膜，避免反复解码和生成标签。优先SSD、分片存储与适度局部读取；保留患者隔离、通道缺失规则和在线几何增强。旧回归缓存需验证后才可复用。
2. 在相同样本与更新预算下实测每卡32/48/64的有效吞吐、取数等待和GPU计算时间。显存占满只能说明容量，不能代表最快速度。机械盘已繁忙时不宜盲目增加worker。
3. 将每epoch抽样预算与完整通道候选池分开，轮换抽样并保留通道内2:1:1。这属于训练方案调整，需同步调整学习率日程和早停口径。
4. 保留全量验证的正确性，优化分类指标的累计实现；每轮只输出一个patch的快照不是当前训练阶段的主要耗时来源。
